# 1 TypeScript 的本质与类型系统基础

## 1.1 TypeScript 的本质与价值

### 定位

这一节先把 TypeScript 的位置摆正。很多人会用 TS，但一到面试就只会说“防止报错、写起来更规范”，这远远不够。

### 必会结论

1. TypeScript 是 JavaScript 的超集，本质上是在编译阶段增加了一套静态类型检查系统。
2. TypeScript 的类型默认只存在于编译期，运行时不会自动保留。
3. TS 的真正价值不是“更严格”，而是让复杂系统的边界更明确、重构更安全、协作成本更低。
4. TS 类型安全不等于运行时安全，对外部输入仍需要运行时校验。

### 核心理解

TypeScript 并没有改变 JavaScript 的运行时对象模型，它做的是“在代码执行前，尽可能早地发现不一致”。所以它最适合处理边界复杂、协作密集、长期演进的项目。资深场景里，我们看重的往往不是单个类型注解，而是如何用类型系统稳定地表达组件契约、API 约束、状态流转、模块边界和重构路径。

### 常见坑

1. 以为 TS 会在运行时自动帮你校验接口返回值。
2. 把 TS 的收益理解成“编辑器提示更舒服”。
3. 以为不用 any 就等于类型系统设计得好。

### 面试展开

如果面试官问 TS 的价值，我会说：TS 的核心收益不是“代码更规范”，而是把复杂系统里的边界显式化。它把很多原本要到运行时才暴露的问题前移到编译期，也让多人协作和重构成本更可控。

## 1.2 any、unknown、never、void

### 定位

这一节是 TS 面试最基础也最容易被追问深度的入口。

### 必会结论

1. any 会关闭类型检查，是最强逃逸类型。
2. unknown 是安全版的 any，接收任何值，但必须先收窄后才能使用。
3. never 表示不可能出现的类型，常用于穷尽检查和不会正常结束的函数。
4. void 更接近“调用方不应依赖返回值”，不等于函数绝对不能返回。

### 核心理解

这四个类型代表四种完全不同的边界语义。any 是放弃约束，unknown 是延迟判断，never 是逻辑上不应到达，void 是调用约定上的“不关心返回值”。资深回答不能只停在定义，而要能说出场景：接第三方输入优先 unknown，穷尽联合类型时用 never，而 any 只能作为非常短期的迁移和逃逸手段。

### 代码抓手

```ts
const value: unknown = 'hello'
if (typeof value === 'string') {
    console.log(value.toUpperCase())
}

type Status = 'success' | 'error' | 'pending'
function handleStatus(status: Status) {
    switch (status) {
        case 'success':
            return '成功'
        case 'error':
            return '失败'
        case 'pending':
            return '处理中'
        default: {
            const exhaustiveCheck: never = status
            throw new Error(`未知状态: ${exhaustiveCheck}`)
        }
    }
}
```

### 常见坑

1. 把 unknown 当成“难用的 any”。
2. 把 never 只理解成“抛错函数返回值”。
3. 说 void 函数什么都不能返回，这不准确。

### 面试展开

更稳的总结是：any 是逃逸，unknown 是边界，never 是穷尽，void 是“返回值不参与约束”。如果一个团队大量使用 any，说明它不是在用 TS 建边界，而是在绕过边界。

## 1.3 类型推断、类型拓宽与 as const

### 定位

这一节解决一个高频问题：TS 明明会推断，为什么资深工程师还经常手动收紧类型。

### 必会结论

1. TypeScript 会根据初始化值、上下文和返回值自动推断类型。
2. 字面量类型默认可能发生拓宽，比如 `'success'` 被推成 string。
3. `as const` 会阻止字面量拓宽，并把属性推成只读字面量类型。
4. 推断不是越智能越好，关键是知道什么时候它会变宽。

### 核心理解

TS 的推断机制非常强，但它默认会在“更精确”和“更可用”之间做平衡。比如对象字面量里的 `'success'` 默认推成 string，是因为编译器认为你可能还会赋别的字符串值。但在状态建模、action type、路由表、组件变体这些场景里，我们常常就是需要它保持字面量精度，这时就要主动用 `as const` 或更精细的类型约束。

### 代码抓手

```ts
const obj = { type: 'success' }
// { type: string }

const obj2 = { type: 'success' } as const
// { readonly type: 'success' }
```

### 常见坑

1. 以为推断结果总是自己想要的最精确版本。
2. 字面量状态建模却忘记收窄，导致判别联合失效。
3. 把 `as const` 当成万能类型修正器，到处乱用。

### 面试展开

我会这样答：资深工程里不是盲信推断，而是知道什么时候推断会拓宽，什么时候要主动收紧。`as const` 的意义就在于把“这是固定字面量，不应该再变宽”明确告诉编译器。

## 1.4 satisfies

### 定位

这一节是中高级 TS 面试里很能拉开差距的点。

### 必会结论

1. satisfies 用于校验某个值满足某个类型约束。
2. 它不会像类型注解那样把原值整体改成更宽的类型。
3. 它比 as 更安全，也比直接标注类型更能保留精确信息。

### 核心理解

as 更像“强制告诉编译器相信我”，带有明显的绕过意味；直接写类型注解，则可能丢失值本身的更精确信息。satisfies 的价值就在于：一边校验结构是否满足要求，一边尽量保留原始字面量推断。这在路由表、变体配置、组件映射表、常量对象建模里非常实用。

### 代码抓手

```ts
const routes = {
    home: '/',
    user: '/user/:id',
} satisfies Record<string, string>
```

### 常见坑

1. 以为 satisfies 会把结果类型直接变成右侧类型。
2. 把 satisfies 和 as 混用成同一语义。
3. 看见能通过校验就忽略了字面量保留的价值。

### 面试展开

如果被问 satisfies，我会说：它的价值不在“又多一个关键字”，而在于“用更安全的方式做结构校验，同时保留更精细的原始推断结果”。

## 1.5 类型收窄、类型守卫与 asserts

### 定位

这一节处理 TypeScript 从“声明类型”走向“运行流程里动态缩小类型”的关键能力。

### 必会结论

1. 类型收窄是 TS 根据运行时判断缩小联合类型范围的机制。
2. 常见收窄方式有 typeof、instanceof、in、判别字段、自定义类型守卫。
3. `x is T` 适合表达“返回 true 时可视为某类型”。
4. asserts 适合表达“如果没抛错，后面就应该按某类型处理”。

### 核心理解

TypeScript 的类型系统不是只在定义点起作用，它还会沿着控制流分析。也就是说，类型信息会跟着 if、switch、return、异常边界一起变化。自定义类型守卫和断言函数的价值，不只是让编译器通过，而是把“运行时判断逻辑”和“类型收窄语义”绑定在一起。

### 代码抓手

```ts
interface User {
    type: 'user'
    name: string
}
interface Admin {
    type: 'admin'
    permissions: string[]
}
type Person = User | Admin

function isUser(person: Person): person is User {
    return person.type === 'user'
}

function assertIsString(value: unknown): asserts value is string {
    if (typeof value !== 'string') {
        throw new Error('value is not string')
    }
}
```

### 常见坑

1. 把类型守卫当成纯语法，不理解它其实在表达控制流语义。
2. 只会写 typeof 收窄，不会设计判别联合。
3. 断言函数里不做真实运行时校验，只图骗过编译器。

### 面试展开

我会说：类型守卫解决的是“某个分支里应该把值看成什么”，asserts 解决的是“如果程序没抛错，后面就必须按某种类型继续执行”。这两者都在把运行时约束同步给类型系统。

## 1.6 第一章速记

### 定位

这一节给 TS 第一章做快速收口。

### 必会结论

1. TS 是编译期静态类型系统，不是运行时自动校验器。
2. any 是逃逸，unknown 是边界，never 是穷尽，void 是返回值约定。
3. 类型推断会拓宽，`as const` 和 satisfies 用来收紧和校验。
4. 类型收窄是控制流分析能力，不只是语法小技巧。

### 面试展开

如果让我用 30 秒收口这一章，我会说：TypeScript 的本质是给 JavaScript 增加编译期边界系统。它真正有价值的地方，不是多写几个类型注解，而是能在复杂控制流和大型工程里把边界持续保持清晰。

# 2 类型建模核心能力

## 2.1 interface 和 type

### 定位

这一节处理 TS 面试里最容易被问成“你更喜欢哪个”的问题。

### 必会结论

1. interface 更适合描述对象结构契约、类实现和可扩展公共接口。
2. type 更灵活，适合联合类型、交叉类型、工具类型和复杂别名组合。
3. interface 支持声明合并，type 不支持。
4. 工程里不应把它们硬做成二选一教条。

### 核心理解

interface 和 type 的区别，不该答成“谁更高级”。更准确的说法是：它们表达能力有重叠，但侧重点不同。interface 更偏“结构契约”，适合领域模型、Props 契约、对外接口；type 更偏“类型运算节点”，适合联合、交叉、映射、条件类型等。大型工程里真正成熟的做法是按表达意图选，而不是强行统一风格。

### 代码抓手

```ts
interface User {
    id: number
    name: string
}

type Status = 'idle' | 'loading' | 'success' | 'error'
type UserWithStatus = User & { status: Status }
```

### 常见坑

1. 把 interface 和 type 讲成简单语法别名。
2. 不知道 interface 有声明合并。
3. 一刀切规定团队只能用一种。

### 面试展开

我会说：interface 更像公共结构契约，type 更像类型表达式容器。资深工程里不是选边站，而是看建模场景用哪种更能表达意图。

## 2.2 联合类型与交叉类型

### 定位

这一节是 TS 建模能力的第一步。

### 必会结论

1. 联合类型 `A | B` 表示“可能是其中之一”。
2. 交叉类型 `A & B` 表示“同时拥有两者能力”。
3. 联合类型更适合状态建模。
4. 交叉类型更适合能力叠加和结构组合。

### 核心理解

联合和交叉看起来只是两个符号，但代表了两种完全不同的建模思路。联合强调分支和可变状态，最典型的是请求状态、组件状态、节点类型；交叉强调拼接和叠加，适合在已有结构上增加能力、标记或扩展字段。很多人一上来就堆可选属性，其实本应用判别联合来表达互斥状态。

### 代码抓手

```ts
type LoadingState = 'idle' | 'loading' | 'success' | 'error'

interface BaseUser {
    id: number
    name: string
}
interface AdminExtra {
    permissions: string[]
}
type AdminUser = BaseUser & AdminExtra
```

### 常见坑

1. 用一个大接口堆很多可选字段，代替判别联合。
2. 把交叉类型理解成运行时对象合并。
3. 以为联合类型不用收窄就能直接访问全部属性。

### 面试展开

更稳的说法是：联合类型更像状态机建模，交叉类型更像能力拼装。一个偏“分支”，一个偏“组合”。

## 2.3 字面量类型与判别联合

### 定位

这一节是 TS 从“会写接口”走向“会做状态建模”的关键。

### 必会结论

1. 字面量类型可以表达非常精细的值域。
2. 判别联合通常通过统一的 type、kind、status 字段来区分分支。
3. 判别联合比“多个可选字段堆在一起”更稳。
4. 它天然适合请求状态、组件状态、节点类型和命令类型建模。

### 核心理解

判别联合的价值，在于它让非法状态组合从类型层面直接消失。比如成功状态必须有 data，失败状态必须有 message，加载状态两者都不该有。如果用一个接口加很多可选字段，你就允许了很多不应存在的组合；用判别联合，编译器会帮你自动约束。

### 代码抓手

```ts
type ApiResult = { status: 'success'; data: string[] } | { status: 'error'; message: string } | { status: 'loading' }

function render(result: ApiResult) {
    switch (result.status) {
        case 'success':
            return result.data.join(',')
        case 'error':
            return result.message
        case 'loading':
            return '加载中'
    }
}
```

### 常见坑

1. 只会写联合类型，不会加判别字段。
2. 判别字段被拓宽成 string，导致联合失效。
3. 漏掉穷尽检查，后期加新分支时静默出错。

### 面试展开

我会说：判别联合是 TS 里非常高价值的建模手段，因为它把“不同状态对应不同结构”表达得非常自然，也能让很多非法状态组合在编译期直接消失。

## 2.4 enum 与字面量联合

### 定位

这一节处理现代前端里“还该不该用 enum”这个高频争议点。

### 必会结论

1. enum 是少数会生成运行时代码的 TS 特性之一。
2. 字面量联合更轻量，也更符合现代前端状态建模习惯。
3. 前端业务状态、请求状态、组件变体，通常更推荐字面量联合。
4. 需要运行时对象映射或兼容旧代码时，再考虑 enum。

### 核心理解

现代前端弱化 enum，并不是因为它不能用，而是因为很多状态建模场景里，字面量联合更轻、更清晰，也更容易和 `as const`、判别联合、对象映射表配合。enum 依然有价值，比如需要运行时枚举对象、数值枚举映射或兼容旧代码，但默认不应无脑上。

### 常见坑

1. 看见一组固定值就本能用 enum。
2. 忽略 enum 的运行时代码成本。
3. 不知道 `const enum` 还有构建链路边界。

### 面试展开

我会这样答：前端业务状态优先用字面量联合，enum 更适合确实需要运行时枚举对象或要兼容既有设计的场景。

## 2.5 品牌类型与名义化模拟

### 定位

这一节是资深 TS 面试里很容易拉开差距的点。

### 必会结论

1. TS 是结构类型系统，默认不关心“类型名”，只关心结构是否兼容。
2. 品牌类型的作用是人为补上一层名义语义。
3. 它适合用户 ID、订单 ID、货币金额等“结构一样但不能混用”的值。

### 核心理解

结构类型系统很适合 JS 世界，但它也意味着两个同样是 string 的值在类型层面天然兼容。品牌类型的价值，就是在不改变运行时值的前提下，通过额外的只读标记把它们区分开。它不是类型体操炫技，而是为了避免领域值误用。

### 代码抓手

```ts
type Brand<T, B extends string> = T & { readonly __brand: B }
type UserId = Brand<string, 'UserId'>
type OrderId = Brand<string, 'OrderId'>
```

### 常见坑

1. 看不懂品牌类型的业务意义，只觉得“多此一举”。
2. 用品牌类型替代所有普通别名，导致复杂度过高。
3. 忘记它只是编译期约束，不会自动做运行时校验。

### 面试展开

更资深的说法是：品牌类型在结构类型系统上补了一层名义语义，适合那些运行时同构、业务语义却必须严格区分的值。

## 2.6 第二章速记

### 定位

这一节收束类型建模主线。

### 必会结论

1. interface 偏结构契约，type 偏类型表达式。
2. 联合适合状态，交叉适合组合。
3. 判别联合比堆可选字段更稳。
4. 现代前端多数状态建模优先字面量联合，而不是 enum。
5. 品牌类型适合模拟名义化边界。

### 面试展开

如果让我 30 秒收口这一章，我会说：TS 的类型建模关键不在语法多，而在于能否把状态、结构、边界和领域语义稳定地表达出来。真正拉开差距的是判别联合、结构契约和边界值设计。

# 3 泛型、keyof、typeof 与索引访问

## 3.1 泛型的本质

### 定位

这一节先把泛型从“高级语法”拉回“类型参数化”这个本质。

### 必会结论

1. 泛型的核心是把类型参数化。
2. 它的目标是在复用逻辑的同时，保持输入输出之间的类型关联。
3. 好的泛型不是越抽象越好，而是抽象后仍然可推断、可约束、可维护。

### 核心理解

泛型不是为了炫技，而是为了表达“这段逻辑适用于很多类型，但这些类型之间仍然有稳定关系”。比如 identity 保证输入什么就输出什么，getProp 保证 key 必须来自对象自身属性，结果类型还要和属性类型关联起来。泛型真正的难点不在 `<>` 语法，而在抽象边界怎么收。

### 代码抓手

```ts
function identity<T>(value: T): T {
    return value
}
const n = identity(1) // number
const s = identity('x') // string
```

### 常见坑

1. 为了“通用”写出过宽泛且无法约束的泛型。
2. 明明不需要泛型，也硬套一个 `<T>`。
3. 只会声明泛型，不会保持类型关联。

### 面试展开

我会说：泛型的价值不只是复用，而是在复用的同时维持输入和输出之间的精确类型关系。抽象如果把这种关系丢了，就只是把信息擦掉了。

## 3.2 泛型约束

### 定位

这一节处理“泛型过宽导致不安全”的高频问题。

### 必会结论

1. 泛型约束通过 extends 控制类型参数范围。
2. 它解决的是“保持抽象同时不丢安全边界”的问题。
3. `K extends keyof T` 是最经典的约束组合之一。

### 代码抓手

```ts
function getProp<T, K extends keyof T>(obj: T, key: K): T[K] {
    return obj[key]
}
const user = { name: 'test', age: 18 }
const name = getProp(user, 'name') // string
```

### 核心理解

无约束泛型很容易把类型系统变成“什么都能进，但里面什么都不敢做”。约束的意义就是告诉编译器：虽然我还想保持抽象，但这个抽象不是无限开放的。keyof 约束就是在表达“传入的 key 必须真的来自对象自身属性”。

### 常见坑

1. 泛型参数过宽，函数内部什么都不能安全访问。
2. key 写成 string，却希望它只接受对象已有字段。
3. 以为加了 extends 就一定有更好推断，实际上还要看整体设计。

### 面试展开

更稳的说法是：泛型约束的作用不是限制炫技，而是把抽象控制在安全边界内。真正好的泛型，既能复用，又不会把类型信息冲掉。

## 3.3 keyof、typeof、索引访问类型

### 定位

这一节是很多工具类型和高级建模的基础组件。

### 必会结论

1. `keyof T` 取对象类型的键联合。
2. typeof 在类型层是“从值提取类型”，不是 JS 运行时的 typeof。
3. `T[K]` 表示索引访问类型，用键获取属性类型。
4. 这三者经常一起使用。

### 代码抓手

```ts
const config = {
    api: '/api',
    timeout: 5000,
}
type Config = typeof config
type ConfigKey = keyof Config // 'api' | 'timeout'
type ApiType = Config['api'] // string
```

### 核心理解

这三者是类型系统里“从现有结构继续推类型”的基础能力。typeof 让你不用重复手写结构，keyof 让你拿到键集合，`T[K]` 让你把键和对应值的类型关联起来。几乎所有“根据对象推导 API”“根据配置生成类型”“根据字段拿返回类型”的设计，都会用到它们。

### 常见坑

1. 把 TS 的 typeof 和 JS 运行时的 typeof 混为一谈。
2. 不知道 `keyof any` 的结果是 `string | number | symbol`。
3. `T[K]` 使用时没保证 K 真的是 T 的键。

### 面试展开

我会说：keyof、typeof 和索引访问类型是 TS 类型运算里最常用的“提取器”。很多高级类型其实都是在它们的基础上继续组合。

## 3.4 第三章速记

### 定位

这一节收束泛型主线。

### 必会结论

1. 泛型是类型参数化，不是高级符号游戏。
2. 泛型约束保证抽象不失控。
3. keyof、typeof、`T[K]` 是高级类型设计的基础积木。

### 面试展开

如果让我收口这一章，我会说：泛型真正重要的是维持类型关联，约束则负责控制抽象边界；而 keyof、typeof 和索引访问类型，则是把已有结构继续推导下去的基础工具。

# 4 条件类型、infer 与工具类型

## 4.1 条件类型

### 定位

这一节是 TS 从“静态描述”走向“类型层面可计算”的关键。

### 必会结论

1. 条件类型本质上是类型层面的 if。
2. 语法是 `T extends U ? X : Y`。
3. 它让类型系统能根据输入类型做分支求值。

### 代码抓手

```ts
type IsString<T> = T extends string ? true : false
type A = IsString<'a'> // true
type B = IsString<number> // false
```

### 核心理解

条件类型的价值，不在于“会写三元表达式”，而在于它让类型系统具备了模式匹配和分支逻辑能力。很多内置工具类型，比如 Exclude、Extract、NonNullable，本质上都建立在条件类型上。

### 常见坑

1. 只会写最简单例子，不知道它是工具类型体系基础。
2. 把条件类型理解成运行时判断。
3. 条件类型写得过于嵌套，导致可读性崩掉。

### 面试展开

我会说：条件类型让 TS 类型系统从“静态标签”升级成“可做分支判断的系统”，这是高级类型设计的关键一步。

## 4.2 分布式条件类型

### 定位

这一节是资深面试高频点，很多人只知道结果，不知道为什么。

### 必会结论

1. 当条件类型左侧是裸类型参数，并传入联合类型时，会发生分发。
2. 这意味着联合类型会被逐项计算。
3. Exclude、Extract 能成立，关键就在这里。

### 代码抓手

```ts
type MyExclude<T, U> = T extends U ? never : T
type Result = MyExclude<string | number | boolean, number>
// string | boolean
```

### 核心理解

所谓分布式条件类型，本质上就是“联合类型成员逐个进入条件分支”。所以 `string | number | boolean` 会分别和 number 比较，再把结果重新并起来。这是很多类型过滤题的核心机制，也是高频追问点。

### 常见坑

1. 只会背 Exclude 结果，不知道为什么是逐项分发。
2. 不知道如何关闭分发。
3. 联合类型过滤题一复杂就彻底失去方向。

### 面试展开

更稳的说法是：分布式条件类型的关键前提是“左边是裸类型参数”。一旦满足这个条件，联合类型就会被拆开逐个求值。

## 4.3 infer

### 定位

这一节讲类型系统里的“模式匹配和提取”。

### 必会结论

1. infer 只能出现在条件类型里。
2. 它的作用是在匹配过程中声明一个待推断的局部类型变量。
3. 它是 ReturnType、Parameters、Awaited 这类工具类型的核心。

### 代码抓手

```ts
type MyReturnType<T> = T extends (...args: any[]) => infer R ? R : never
type MyParameters<T> = T extends (...args: infer P) => any ? P : never
```

### 核心理解

infer 不是什么神秘语法，它本质上就是“如果这个模式能匹配上，把其中一段类型提取出来命名”。比如函数类型里把返回值提成 R，把参数元组提成 P，Promise 里把被包裹的值提成 U。真正高价值的点，是知道它在做类型模式匹配，而不是背几个例子。

### 常见坑

1. 以为 infer 可以单独使用。
2. 看见 infer 就慌，实际上它只是“提取一段类型”。
3. 不会把 infer 和条件类型配合理解。

### 面试展开

我会说：infer 就是类型层的“局部变量捕获”，必须放在条件类型的匹配模式里使用。它让我们能从函数、Promise、数组、元组等结构里把想要的类型片段提取出来。

## 4.4 Awaited

### 定位

这一节补一个现代 TS 高频点，也顺手把 async/await 的类型语义串起来。

### 必会结论

1. `Awaited<T>` 用于递归解包 Promise 最终值。
2. 它模拟的是 await 在类型系统里的结果。
3. 它本质上就是条件类型和 infer 的组合。

### 代码抓手

```ts
type MyAwaited<T> = T extends PromiseLike<infer U> ? MyAwaited<U> : T
type A = MyAwaited<Promise<Promise<string>>> // string
```

### 核心理解

Awaited 的价值不只是“多一个工具类型”，而是它把 async/await 的运行时解包语义映射到了类型系统中。看到它，你就应该能联想到 Promise 递归展开、thenable 兼容和 infer 提取。

### 常见坑

1. 以为 Awaited 只解一层 Promise。
2. 不知道它和 async/await 语义有关。
3. 看见 PromiseLike 就直接跳过不理解。

### 面试展开

我会说：Awaited 很适合用来理解 TS 工具类型的设计方式，因为它把“运行时 await 怎么解包 Promise”转成了类型层表达。

## 4.5 内置工具类型

### 定位

这一节不只是背名字，而是讲它们底层依赖了什么。

### 必会结论

1. Partial、Required、Readonly、Pick、Record 建立在映射类型上。
2. Exclude、Extract、NonNullable 建立在条件类型上。
3. ReturnType、Parameters、InstanceType、Awaited 建立在条件类型和 infer 上。
4. 资深面试不会只问“怎么用”，而会问“底层怎么写”。

### 代码抓手

```ts
type MyPartial<T> = {
    [K in keyof T]?: T[K]
}

type MyPick<T, K extends keyof T> = {
    [P in K]: T[P]
}

type MyNonNullable<T> = T extends null | undefined ? never : T
```

### 核心理解

工具类型真正重要的不是名字，而是它们是对“映射类型、条件类型、infer”这些底层能力的标准化封装。理解底层以后，不但面试能手写，项目里也知道什么时候该用现成工具，什么时候该写自定义类型工具。

### 常见坑

1. 只背 API 名字，不知道底层原理。
2. 手写工具类型时忘记约束泛型边界。
3. 一上来就写复杂体操，导致类型可读性极差。

### 面试展开

我会说：内置工具类型不是孤立 API，它们是 TS 类型系统几类核心机制的组合产物。真正理解以后，既能手写，也能判断什么时候不该写。

## 4.6 第四章速记

### 定位

这一节收束高级类型主线。

### 必会结论

1. 条件类型是类型层面的 if。
2. 分布式条件类型解释了联合类型过滤。
3. infer 负责在匹配中提取局部类型变量。
4. 工具类型本质是映射类型、条件类型和 infer 的组合。

### 面试展开

如果让我 30 秒收口这一章，我会说：TS 高级类型系统真正的核心不是工具类型名字，而是三件事：条件类型负责分支，infer 负责提取，映射类型负责批量变换。大多数高频手写题和内置工具类型都可以归到这三类机制上。

# 5 函数、类与兼容性

## 5.1 函数类型、重载与 this 参数

### 定位

这一节处理 TS 在“函数签名表达”和“调用约束”上的高频问题。很多人会写函数类型，但一到重载、this 参数、联合签名边界就容易答浅。

### 必会结论

1. 函数类型的核心是参数列表和返回值。
2. 函数重载是“多个对外签名 + 一个实现签名”。
3. this 参数只存在于类型层，不会进入运行时代码。
4. 如果只是参数联合且返回值逻辑一致，通常联合类型比重载更简单。

### 代码抓手

```ts
function format(value: string): string
function format(value: number): string
function format(value: string | number): string {
    return String(value)
}

function handler(this: HTMLButtonElement, event: MouseEvent) {
    console.log(this.disabled, event.type)
}
```

### 核心理解

重载真正要表达的是“不同输入对应不同的更精确输出”，而不是“只要复杂一点就上重载”。实现签名通常比对外签名更宽，它只是为了让函数体能统一处理各种输入；调用方真正看到的，是前面那几条重载签名。this 参数也很值得单独说明，它的意义是把调用上下文约束显式化，尤其适合 DOM 回调、老代码库和需要动态 this 的工具函数。

### 常见坑

1. 把实现签名当成对外暴露的最终签名。
2. 明明联合类型就够，却硬写成多组重载。
3. 以为 this 参数会真的出现在运行时参数列表里。

### 面试展开

我会说：函数重载适合表达“不同输入对应不同输出”的精细约束；如果只是输入类型不同但处理语义一致，联合类型通常更简单。this 参数则是 TS 专门提供的类型能力，用来显式约束调用上下文，它本身不会出现在运行时代码里。

## 5.2 类、抽象类与 interface 的边界

### 定位

这一节处理“接口和抽象类怎么选”这个资深面试常问点。

### 必会结论

1. class 是运行时存在的，interface 只存在于编译期。
2. `abstract class` 适合表达带部分默认实现的骨架。
3. interface 更适合纯结构契约，`abstract class` 更适合抽象基类。
4. implements 只检查实例侧结构，不会替你校验静态侧设计。

### 代码抓手

```ts
abstract class BaseService {
    abstract request(url: string): Promise<unknown>
    log(message: string) {
        console.log(message)
    }
}

interface Cacheable {
    set(key: string, value: unknown): void
}

class ApiService extends BaseService implements Cacheable {
    async request(url: string) {
        return fetch(url).then(res => res.json())
    }
    set(key: string, value: unknown) {
        localStorage.setItem(key, JSON.stringify(value))
    }
}
```

### 核心理解

接口更像“你至少要长成这个样子”，抽象类更像“我先给你一部分公共骨架，剩下的你自己补”。所以当你只需要描述结构契约时，interface 往往更轻；当你既要统一约束，又要沉淀公共实现、生命周期骨架、日志能力、模板方法时，抽象类会更自然。资深回答里最好把“编译期结构约束”和“运行时继承复用”分开讲。

### 常见坑

1. 把 interface 和抽象类讲成“功能几乎一样”。
2. 明明只需要结构契约，却为了“面向对象”强上基类。
3. 不知道 implements 检查的是实例结构，不是静态成员设计。

### 面试展开

比较稳的说法是：接口更偏纯契约，抽象类更偏带默认实现的骨架。前者负责描述边界，后者负责复用行为。工程里怎么选，不看“哪个更高级”，而看你需不需要运行时继承和公共实现。

## 5.3 结构类型系统

### 定位

这一节是 TS 面试里必须讲清的底层前提，因为很多兼容性规则都建立在这里。

### 必会结论

1. TypeScript 采用结构类型系统，不看类型名，只看结构是否兼容。
2. 两个类型只要结构满足要求，就可以互相赋值或作为参数传递。
3. 对象字面量会触发额外属性检查，变量赋值通常更宽松。
4. 结构类型系统贴近 JS 对象模型，但也会带来“过宽松”的问题。

### 代码抓手

```ts
interface User {
    name: string
}

interface Person {
    name: string
}

const user: User = { name: 'miaoma' }
const person: Person = user

function printUser(target: User) {
    console.log(target.name)
}

const temp = { name: 'miaoma', age: 18 }
printUser(temp)
// printUser({ name: 'miaoma', age: 18 })
```

### 核心理解

TS 之所以采用结构类型系统，是因为它要尽量贴近 JavaScript 的对象世界。JS 里对象天然更关注“有没有这些属性和能力”，而不是“你是不是这个名义类型”。这让类型复用和渐进接入都更自然，但代价是有些场景会显得过宽松，所以 TS 又补了额外属性检查、只读约束、品牌类型这些机制来修正边界。

### 常见坑

1. 以为类型名不一样就一定不兼容。
2. 不理解为什么对象字面量和变量赋值行为不完全一样。
3. 把结构兼容误解成“TS 没有边界能力”。

### 面试展开

我会说：TS 采用结构类型系统，是因为它要贴近 JavaScript 的对象模型。兼容性的关键不是名字，而是结构是否满足要求。也正因为如此，资深工程里常常还需要额外属性检查、品牌类型和更强的边界设计来避免过度宽松。

## 5.4 协变、逆变与函数兼容

### 定位

这一节是资深 TS 面试里最容易被追问抽象能力的一块。

### 必会结论

1. 返回值类型通常更接近协变，返回更具体的结果通常更安全。
2. 函数参数在 strictFunctionTypes 下更接近逆变。
3. 这类规则的核心不是背名词，而是理解“安全替换”。
4. 方法参数为了兼容历史代码，实际行为会比纯理论更复杂。

### 代码抓手

```ts
interface Animal {
    name: string
}

interface Dog extends Animal {
    bark(): void
}

type Handler<T> = (value: T) => void

let handleAnimal: Handler<Animal> = animal => {
    console.log(animal.name)
}

let handleDog: Handler<Dog> = dog => {
    dog.bark()
}

handleDog = handleAnimal
// handleAnimal = handleDog
```

### 核心理解

理解协变和逆变，最好的方式不是死背术语，而是看“一个实现能不能安全替换另一个位置”。如果某个位置本来要求能处理 Dog，那给它一个能处理所有 Animal 的函数通常是安全的，因为 Dog 本来就是 Animal；反过来，如果它可能收到普通 Animal，你却传一个只能处理 Dog 的函数，就不安全了。返回值则相反，给更具体的结果一般没问题。TS 在这里既要追求类型安全，也要兼顾 JS 生态兼容，所以实际规则比纯学术版本更务实。

### 常见坑

1. 只会背“协变、逆变”这两个词，不会解释安全替换逻辑。
2. 不知道 strictFunctionTypes 会显著影响函数兼容行为。
3. 把方法参数和普通函数参数的兼容规则简单混成一套。

### 面试展开

我会说：协变和逆变的本质是看“这个实现能不能安全替换原约定”。返回值越具体通常越安全，参数类型则更敏感，所以在严格函数类型下更接近逆变。真正要讲清的不是名词，而是替换安全性。

## 5.5 第五章速记

### 定位

这一节收束函数、类和兼容性主线。

### 必会结论

1. 重载适合表达更精确的输入输出对应关系，this 参数是纯类型能力。
2. interface 偏结构契约，抽象类偏运行时骨架复用。
3. TS 的底层兼容逻辑建立在结构类型系统上。
4. 协变、逆变本质都在回答“能不能安全替换”。

### 面试展开

如果让我 30 秒收口这一章，我会说：TS 在函数和类上的关键，不是把面向对象概念重新背一遍，而是理解签名如何表达边界、结构类型系统如何决定兼容、以及替换安全性为什么会影响函数参数和返回值。

# 6 声明文件与 JS 互操作

## 6.1 .d.ts 的作用

### 定位

这一节处理 TS 和 JavaScript 生态对接时最基础也最实用的能力。

### 必会结论

1. `.d.ts` 用于为 JavaScript 代码或外部模块补充类型信息。
2. 声明文件只参与编译期类型系统，不会生成实际运行时代码。
3. 它的价值是让黑盒依赖进入类型系统，能被 IDE 和编译器正确理解。
4. 声明来源既可能是官方自带，也可能来自 `@types/*` 或团队自定义。

### 核心理解

TS 不可能只在“全 TS 世界”里工作，它必须和大量已有 JS 模块、全局脚本、第三方 SDK、运行时注入能力协作。`.d.ts` 做的事情，就是把这些运行时已经存在的东西，用编译器能理解的方式描述出来。资深场景里，它的意义不是“让编辑器不报错”，而是把外部边界也纳入可维护体系。

### 常见坑

1. 以为写了 `.d.ts` 就等于真的实现了对应运行时能力。
2. 类型声明和真实运行时 API 不一致，导致“编译通过、运行出错”。
3. 把声明文件当成随便兜底的 any 容器。

### 面试展开

我会说：声明文件的核心价值，是把没有原生类型信息的 JS 能力接入 TS 类型系统。它只影响编译期，不会生成运行时代码，所以它描述的前提必须和真实运行时保持一致。

## 6.2 模块声明

### 定位

这一节处理“没有类型的第三方包怎么接入”这个高频实战题。

### 必会结论

1. `declare module 'xxx'` 用来给某个模块路径声明类型。
2. 声明里的导出方式，要和真实模块的导出方式匹配。
3. 它适合无类型第三方包、虚拟模块或特殊构建产物。
4. 模块名必须和真实导入路径一致，否则声明不会生效。

### 代码抓手

```ts
declare module 'legacy-sdk' {
    export interface InitOptions {
        appId: string
        debug?: boolean
    }

    export function init(options: InitOptions): void
    export function request<T>(url: string): Promise<T>
}
```

### 核心理解

模块声明本质是在告诉编译器：“当你看到这个导入路径时，请按我这里描述的类型去理解它。”它最核心的要求不是语法会写，而是声明的结构必须贴合真实模块形态，比如到底是默认导出、命名导出、函数导出还是对象导出。这里一旦写错，后面的类型推断和消费方式都会偏。

### 常见坑

1. 模块名写错，结果声明完全不生效。
2. 把默认导出和命名导出写混。
3. 对已经有完善类型的模块重复声明，造成冲突。

### 面试展开

更稳的说法是：模块声明不是在“编一个类型故事”，而是在把真实模块的暴露面准确映射给编译器。关键不在 `declare module` 这几个字，而在导出结构要和真实模块保持一致。

## 6.3 全局扩展

### 定位

这一节处理浏览器全局变量、宿主注入对象和传统脚本接入时的常见需求。

### 必会结论

1. `declare global` 用来扩展全局作用域里的类型。
2. 常见场景包括扩展 Window、全局变量、全局接口和宿主注入对象。
3. 这类声明通常需要放在模块作用域中，常见做法是文件里写一个 `export {}`。
4. 全局扩展要非常克制，因为它会影响整个工程的类型环境。

### 代码抓手

```ts
export {}

declare global {
    interface Window {
        $SDK: {
            init(config: { appId: string }): void
            request<T>(url: string): Promise<T>
        }
    }
}
```

### 核心理解

全局扩展的本质，是告诉编译器“这个全局环境比默认认知多了一些东西”。它很适合接第三方脚本 SDK、老系统全局对象、宿主注入 API，但也因为影响范围太大，所以比普通模块声明更要谨慎。资深工程里，能模块化的尽量模块化，只有真的存在全局运行时前提时才做全局增强。

### 常见坑

1. 忘记让声明文件处于模块作用域，导致 `declare global` 失效或行为异常。
2. 在全局里堆太多业务类型，污染工程边界。
3. 只补了类型声明，却没确认运行时对象是否真的存在。

### 面试展开

我会说：全局扩展适合描述宿主环境里真实存在的全局能力，比如 `window.$SDK`。但它的代价是影响全局类型环境，所以应该谨慎使用，优先模块化，只有在运行时天然就是全局对象时才这样建模。

## 6.4 模块增强、类型目录与管理边界

### 定位

这一节处理声明文件里更资深的内容，也就是“给已有模块追加类型能力”。

### 必会结论

1. 模块增强用于扩展已有模块的声明，而不是重写整个模块。
2. 它非常适合框架扩展点，比如路由元信息、请求配置、组件实例属性。
3. 自定义类型目录必须被 include、files 或相关配置覆盖到，否则声明不会生效。
4. typeRoots 能改变类型查找根目录，使用时要非常谨慎。

### 代码抓手

```ts
import 'vue-router'

declare module 'vue-router' {
    interface RouteMeta {
        requiresAuth?: boolean
        title?: string
    }
}
```

### 核心理解

模块增强更像“在原有声明上补一层业务定制”，它特别适合那些框架已经给出扩展入口、但默认类型还不够表达业务约束的场景。和普通模块声明相比，它不是从零定义，而是在已有模块类型基础上做增量补充。与此同时，声明文件管理也很重要，很多“为什么类型没生效”的问题，本质上不是写错了，而是文件根本没被 TS 收进工程。

### 常见坑

1. 不知道模块增强是在已有声明上追加，而不是完全替换。
2. 自定义 types/ 目录没被 include 到，结果声明完全不生效。
3. 误用 typeRoots，把默认的类型查找路径也一起改坏。

### 面试展开

比较稳的答法是：模块增强适合在框架给定边界上做业务扩展，比如补 RouteMeta、补请求配置、补全局组件属性。真正高频的坑反而不是语法，而是声明文件归属、工程收录和查找路径管理。

## 6.5 第六章速记

### 定位

这一节收束声明文件和 JS 互操作主线。

### 必会结论

1. `.d.ts` 负责把外部 JS 能力接入 TS 类型系统。
2. 模块声明关注导入路径和真实导出结构的一致性。
3. 全局扩展要克制使用，因为它会影响整个工程。
4. 模块增强和类型目录管理是大型项目里声明体系稳定的关键。

### 面试展开

如果让我 30 秒收口这一章，我会说：声明文件的价值不只是补提示，而是把原本黑盒的 JS 依赖接进类型系统。真正要注意的是三件事：声明是否贴近真实运行时、作用域是否正确、工程配置是否真的把这些类型收进来了。

# 7 tsconfig 与工程化配置

## 7.1 strict 为什么是主线配置

### 定位

这一节处理 TS 工程化里最核心的一项配置，也是资深面试几乎必问点。

### 必会结论

1. strict 是一组高价值严格规则的总开关。
2. 常见关键子项包括 strictNullChecks、noImplicitAny、noImplicitThis、strictFunctionTypes、strictPropertyInitialization。
3. 中大型项目通常应该开启 strict。
4. 遇到迁移成本高的问题，应该局部治理，而不是一把关掉全局严格模式。

### 代码抓手

```json
{
    "compilerOptions": {
        "strict": true,
        "noImplicitAny": true,
        "strictNullChecks": true,
        "strictFunctionTypes": true
    }
}
```

### 核心理解

strict 的真正价值，不是“让你多写点代码”，而是把很多高代价问题尽量前移到编译期。空值边界、隐式 any、this 上下文、函数参数兼容、类属性初始化，这些在大型项目里都非常容易演变成维护成本。资深视角下，strict 不是锦上添花，而是类型治理的底座。

### 常见坑

1. 为了短期通过编译，直接把 strict 整体关掉。
2. 滥用非空断言 `!`，把严格模式变成表面严格。
3. 只知道 `strict: true`，不知道真正影响项目的是哪些子项。

### 面试展开

我会说：strict 的价值不是“更烦”，而是让很多高价值边界问题在编译期暴露。大型项目里，关闭严格模式的短期成本看起来低，但长期维护成本会迅速放大。

## 7.2 module、moduleResolution 与环境匹配

### 定位

这一节处理 TS 工程配置里最容易被机械复制、但实际很依赖运行环境的一块。

### 必会结论

1. module 决定模块输出语义，moduleResolution 决定模块查找策略。
2. 前端打包器项目通常更适合 `moduleResolution: 'bundler'`。
3. Node 原生 ESM / CJS 混用场景更需要关注 node16 或 nodenext。
4. 这组配置不能脱离真实运行环境和工具链单独讨论。

### 代码抓手

```json
{
    "compilerOptions": {
        "module": "ESNext",
        "moduleResolution": "bundler"
    }
}
```

### 核心理解

很多人把 module 和 moduleResolution 当成一回事，其实不是。前者更偏“我要按什么模块语义产出和理解代码”，后者更偏“编译器在解析导入路径时该遵循什么规则”。现代前端项目里，Vite、Webpack、Rspack 这类打包器通常更适合 bundler；如果是 Node 原生执行、还涉及 ESM/CJS 互操作，就要更谨慎地选 node16 或 nodenext。

### 常见坑

1. 把 module 和 moduleResolution 混成一个概念。
2. 在 Node 场景里照搬前端项目的 bundler 配置。
3. 忽略 `package.json` 的 exports、types 和真实解析链路。

### 面试展开

比较稳的说法是：TS 的模块配置必须和真实运行环境匹配。前端 bundler 项目、Node 原生项目、库开发项目的选择逻辑并不一样，不能机械复制模板。

## 7.3 baseUrl、paths 与运行时一致性

### 定位

这一节处理“TS 能过但运行时报模块找不到”的经典问题。

### 必会结论

1. baseUrl 和 paths 用于给 TypeScript 提供路径映射能力。
2. TS 能识别路径别名，不代表 bundler、测试环境和 Node 运行时也能识别。
3. 路径别名配置必须在编译器、打包器、测试框架之间保持一致。
4. 路径别名是提高可维护性，不是掩盖层级混乱的工具。

### 代码抓手

```json
{
    "compilerOptions": {
        "baseUrl": ".",
        "paths": {
            "@/*": ["src/*"]
        }
    }
}
```

### 核心理解

paths 解决的主要是开发体验和工程可维护性，比如避免一串 `../../../`。但它只是 TypeScript 侧的解析提示，并不会自动改造真实运行时的模块解析。因此只配 tsconfig 而不同步 Vite、Webpack、Vitest、Jest、Node 配置，是非常典型的坑。资深回答里最好把“类型解析”和“运行时解析”分开讲。

### 常见坑

1. 只配了 tsconfig，结果运行时或测试环境解析失败。
2. 路径别名过多，反而让模块边界更混乱。
3. 把 paths 当成跨包依赖治理手段，掩盖真实架构问题。

### 面试展开

我会说：paths 的价值在于改善可读性和维护性，但它只解决编译器侧的路径映射。真正上线能不能跑，还取决于 bundler、测试框架和运行时解析配置是否同步。

## 7.4 skipLibCheck、incremental、declaration

### 定位

这一节处理性能与产物配置的三个高频选项。

### 必会结论

1. skipLibCheck 用于跳过第三方声明文件检查，常见于应用项目提速。
2. incremental 用于开启增量编译，提高二次构建速度。
3. declaration 用于生成 `.d.ts`，在库和共享包场景更重要。
4. 这些配置都不是“永远越开越好”，要看项目角色和收益。

### 代码抓手

```json
{
    "compilerOptions": {
        "skipLibCheck": true,
        "incremental": true,
        "declaration": true,
        "tsBuildInfoFile": "./.tsbuildinfo"
    }
}
```

### 核心理解

这三个配置分别代表三类工程目标。skipLibCheck 偏性能和现实妥协，很多应用项目会开，因为第三方库声明一旦很多，完整检查成本高；incremental 偏本地和 CI 构建效率；declaration 偏包产物输出，对组件库、SDK、monorepo 共享包尤其关键。资深场景下，关键不是会不会开，而是知道为什么开、开了有什么代价。

### 常见坑

1. 把 skipLibCheck 当成“类型问题彻底没了”。
2. 普通应用项目无差别生成声明产物，增加构建成本却没收益。
3. 开了增量编译却不管理缓存文件位置和 CI 策略。

### 面试展开

我会说：这几个配置分别对应性能、构建效率和产物输出诉求。应用和库的策略不一样，真正成熟的做法是基于项目角色选，而不是照抄一套“万能配置”。

## 7.5 类型性能优化

### 定位

这一节处理大型项目里经常被忽略，但一旦出问题就很痛的主题。

### 必会结论

1. 类型系统本身也会消耗编译性能和 IDE 性能。
2. 超深递归类型、超大联合类型、复杂分布式条件类型都可能拖慢工程。
3. 复杂类型应尽量抽离、复用并命名，而不是无限内联。
4. 类型体操不是越炫越好，可维护性和编译成本同样重要。

### 核心理解

很多人以为“类型只是注释”，其实 TS 编译器要真实计算这些类型关系。只要类型开始递归、分发、组合、推断，它就已经在做一套不小的计算任务了。所以资深工程里，我们不仅关心类型能不能表达出来，还关心表达成本是否可接受。过度复杂的类型设计，往往会让 IDE 卡顿、编译变慢、团队维护门槛升高。

### 常见坑

1. 为了炫技写超复杂类型体操，结果项目和 IDE 都变慢。
2. 递归类型没有清晰终止条件。
3. 明明可以拆成命名类型，却全部写成一条超长内联表达式。

### 面试展开

更稳的说法是：类型也是会消耗性能的。大型项目里，优秀的 TS 设计不仅要“表达得出来”，还要“编译得动、团队看得懂、重构改得动”。

## 7.6 第七章速记

### 定位

这一节收束 tsconfig 与工程化主线。

### 必会结论

1. strict 是类型治理的底座配置。
2. 模块相关配置必须和真实运行环境匹配。
3. paths 只解决 TS 解析，不自动解决运行时解析。
4. 性能类配置和类型设计都要看项目角色与长期收益。

### 面试展开

如果让我 30 秒收口这一章，我会说：tsconfig 不只是“让项目能编译”，而是在决定类型边界、模块解析、构建产物和开发效率。资深工程里最关键的是配置和真实环境一致，而不是把网上模板原样搬进项目。

# 8 TS 与 Vue/React/API 建模实战

## 8.1 Vue 3 + TS

### 定位

这一节处理 TS 在 Vue 3 里最常见也最容易写松的边界。

### 必会结论

1. ref 在空初值、异步赋值、DOM 引用场景里通常要显式提供泛型。
2. reactive 解构会丢失响应式语义，通常要配合 toRefs 或直接保留对象访问。
3. defineProps、withDefaults、defineEmits、defineExpose 应该一起形成组件契约。
4. Vue + TS 的重点不是“处处写泛型”，而是把 Props、状态边界、事件和空值处理收紧。

### 代码抓手

```ts
import { reactive, ref, toRefs } from 'vue'

interface User {
    name: string
    age: number
}

const count = ref<number>(0)
const currentUser = ref<User | null>(null)

const state = reactive({
    loading: false,
    user: null as User | null,
})

const { loading, user } = toRefs(state)
```

### 核心理解

Vue 里最容易被忽略的，不是语法层，而是响应式与类型边界怎么协同。比如 `ref(null)` 如果不显式写类型，后面常常会把推断带歪；reactive 如果直接结构赋值，响应式链路和类型语义都可能一起丢掉。资深工程里真正有价值的，是把组件契约、事件约束、异步空值、接口状态这些位置收紧，而不是把每一行都写成花哨的泛型展示。

### 常见坑

1. `ref(null)` 不写联合类型，后续赋值和访问一团混乱。
2. 直接解构 reactive 导致响应式丢失。
3. defineProps 只写了表面类型，没有把默认值和可选边界一起考虑。

### 面试展开

我会说：Vue + TS 的关键不在“多写类型”，而在几个高风险边界上收紧类型，比如 `ref<T | null>`、Props 契约、事件参数和异步状态。这样既能保住类型安全，也不会把组件写得很重。

## 8.2 React + TS

### 定位

这一节处理 React 里最常见的 TS 边界问题。

### 必会结论

1. useState 的初始值会直接影响推断结果。
2. useRef 在空值场景里通常需要 `T | null`。
3. React 事件对象要使用对应的事件类型，如 `React.ChangeEvent<HTMLInputElement>`。
4. 泛型组件、Hooks 返回值和组件 Props 组合约束，是 React + TS 的高频深问点。

### 代码抓手

```ts
import { useRef, useState } from 'react'

interface User {
    id: number
    name: string
}

const [user, setUser] = useState<User | null>(null)
const inputRef = useRef<HTMLInputElement | null>(null)

function handleChange(event: React.ChangeEvent<HTMLInputElement>) {
    console.log(event.target.value)
}
```

### 核心理解

React + TS 经常出问题的地方，不是写不出类型，而是初值推断和空值边界没有处理好。比如 `useState([])` 很容易把后续元素类型推宽或推歪，`useRef(null)` 不写泛型就会让后续 DOM 使用变得别扭。资深回答里最好把“推断受初值影响”和“组件边界契约要清晰”这两点讲出来。

### 常见坑

1. 让 useState 靠初值盲推，结果推断过宽或不符合业务。
2. useRef 没有处理空值，直接访问实例属性。
3. 事件类型写成原生 DOM 类型，和 React 合成事件模型混淆。

### 面试展开

我会说：React + TS 的关键不是 API 类型会不会写，而是状态初值、Ref 空值和组件 Props 组合约束是否稳。很多类型问题，其实都从第一次初始化就埋下来了。

## 8.3 API 建模与状态建模

### 定位

这一节是 TS 在大型项目里最有业务价值的部分之一。

### 必会结论

1. TS 最大的工程价值之一，是把前后端接口边界和 UI 状态边界稳定地建模出来。
2. 常见建模对象包括请求参数、响应体、分页结构、错误结构和状态机式 UI 状态。
3. 响应泛型要和业务层封装结合，而不是只停在“写个 `ApiResponse<T>`”。
4. 判别联合比一堆可选字段更适合表达异步状态流转。

### 代码抓手

```ts
interface ApiResponse<T> {
    code: number
    message: string
    data: T
}

interface PageResult<T> {
    list: T[]
    total: number
}

type UserListResponse = ApiResponse<
    PageResult<{
        id: number
        name: string
    }>
>

type LoadState<T> = { status: 'idle' } | { status: 'loading' } | { status: 'success'; data: T } | { status: 'error'; message: string }
```

### 核心理解

真正成熟的 API 建模，不是写几个接口名字，而是让“请求、响应、错误、状态、分页、列表项、组件消费方式”形成一条统一边界。很多系统出问题，不是没有 TS，而是类型只停在最外层 DTO，没有穿透到状态机、Hook、Store、组件 Props 和错误处理链路里。资深工程里，类型设计要服务于整个数据流，而不是孤立地服务某个接口文件。

### 常见坑

1. 只给接口返回值写类型，不建模错误状态和 UI 状态。
2. 成功、失败、加载中全堆成一堆可选字段。
3. 响应泛型写得很漂亮，但业务层依然到处 `as any`。

### 面试展开

我会说：TS 在 API 场景里的真正价值，是把“后端返回什么”和“前端怎么消费这些状态”串起来建模。只写 DTO 很浅，真正要建的是接口边界和状态流转边界。

## 8.4 TS 与运行时校验的边界

### 定位

这一节是资深面试里必须答清的现实边界。

### 必会结论

1. TypeScript 只负责编译期静态检查，不负责运行时数据真实性。
2. 后端接口返回、用户输入、URL 参数、本地存储反序列化、第三方 SDK 返回都需要运行时校验。
3. TS 和运行时校验不是替代关系，而是分工不同。
4. 常见方案包括 zod、valibot 和自定义 schema validator。

### 代码抓手

```ts
import { z } from 'zod'

const UserSchema = z.object({
    id: z.number(),
    name: z.string(),
})

type User = z.infer<typeof UserSchema>

async function fetchUser(): Promise<User> {
    const raw = await fetch('/api/user').then(res => res.json())
    return UserSchema.parse(raw)
}
```

### 核心理解

TS 解决的是“代码内部一致性”，运行时校验解决的是“外部输入真实性”。如果你把接口返回直接断言成某个类型，编译器会很开心，但真实世界并不会因此变得可信。资深面试里，一定要明确说出：只要数据来自进程外、网络外、用户外、存储外，就要考虑运行时校验；而不是因为用了 TS 就误以为已经全链路安全。

### 常见坑

1. 以为“后端约定好了”就不需要运行时校验。
2. 用 as 把未知数据硬断言成目标类型。
3. 把运行时校验和 TS 类型写成两份完全脱节的系统。

### 面试展开

我会说：TS 类型安全不等于运行时安全。TS 只保证我们“按自己声明的方式写代码”，但不保证外部数据真的符合声明。对接口、表单、URL、缓存和第三方输入，仍然要做运行时校验。

## 8.5 第八章速记

### 定位

这一节收束 TS 在框架和 API 场景里的落地思路。

### 必会结论

1. Vue 和 React 里的关键不是“多写类型”，而是收紧高风险边界。
2. API 建模要覆盖响应、错误和状态流转，而不是只写 DTO。
3. 判别联合很适合表达异步状态。
4. TS 和运行时校验必须配合使用。

### 面试展开

如果让我 30 秒收口这一章，我会说：TS 在真实项目里最有价值的地方，是把组件契约、状态边界和 API 数据流稳定地建起来。同时要记住一件事，TS 只解决编译期一致性，外部输入仍然需要运行时校验。

# 9 高频类型手写与题型

## 9.1 为什么要会手写工具类型

### 定位

这一节先把“为什么面试总爱考这些题”讲清楚。

### 必会结论

1. 手写工具类型不是为了背答案，而是为了检验你是否真的理解映射类型、条件类型和 infer。
2. 这类题考的不只是会不会写，还考边界意识和抽象能力。
3. 面试版实现要短平快，工程版更关注可读性和复用。

### 核心理解

高频手写题之所以常出现，是因为它能很快区分“只是会用内置工具类型”和“真的理解底层机制”的差别。比如 Partial 看的是映射类型，Exclude 看的是分布式条件类型，ReturnType 看的是 infer。真正成熟的回答，不会把它写成纯记忆题，而是能顺手讲出底层依赖了哪类能力。

### 常见坑

1. 只背代码，不知道每一题在考什么。
2. 手写时不加泛型约束，导致类型边界很松。
3. 工具类型越写越复杂，却讲不清业务价值。

### 面试展开

我会说：手写工具类型真正想考的，是你是否理解 TS 类型系统的基本构件，而不是是否把某一题模板背熟。

## 9.2 Partial、Required、Readonly

### 定位

这一节是映射类型最基础的一组题。

### 必会结论

1. 这三题本质都建立在映射类型上。
2. Partial 是把属性变可选，Required 是去掉可选，Readonly 是加只读。
3. 它们的关键在于 keyof 和映射修饰符。

### 代码抓手

```ts
type MyPartial<T> = {
    [K in keyof T]?: T[K]
}

type MyRequired<T> = {
    [K in keyof T]-?: T[K]
}

type MyReadonly<T> = {
    readonly [K in keyof T]: T[K]
}
```

### 常见坑

1. 不知道 `-?` 是去掉可选修饰。
2. 把只读和深只读混为一谈。
3. 忘记这是浅层变换，不会递归处理嵌套对象。

### 面试展开

比较稳的说法是：这三题本质上都是“遍历每个键，再改属性修饰符”，核心机制是映射类型，而不是 API 名字本身。

## 9.3 Pick、Omit、Record

### 定位

这一节处理属性筛选和重新构造结构的题。

### 必会结论

1. Pick 是从原类型里挑一部分键。
2. Omit 常见写法是 `Pick + Exclude` 组合。
3. Record 是用一组键构造新的键值映射类型。

### 代码抓手

```ts
type MyPick<T, K extends keyof T> = {
    [P in K]: T[P]
}

type MyOmit<T, K extends keyof any> = Pick<T, Exclude<keyof T, K>>

type MyRecord<K extends keyof any, T> = {
    [P in K]: T
}
```

### 核心理解

Pick 和 Omit 的价值，在于它们让类型建模更偏“组合式”而不是“重写式”。比如接口字段做裁剪、表单类型从领域模型挑字段、DTO 和 ViewModel 的差异表达，都常用到它们。Record 则更适合表达“给一组键统一映射到同一类值”的结构，比如状态表、映射表、字典对象。

### 常见坑

1. Pick 的第二个泛型没加 `keyof T` 约束。
2. 不理解为什么 Omit 经常是 `Pick + Exclude`。
3. 用 `Record<string, T>` 过度宽化本来更精确的键集合。

### 面试展开

我会说：这一组题都在考“如何基于已有结构再组合出新结构”。真正高频的能力不是默写，而是知道什么时候该选筛选、什么时候该选重构。

## 9.4 Exclude、Extract、NonNullable

### 定位

这一节是条件类型过滤题的代表。

### 必会结论

1. Exclude 是把联合类型里可分配给目标类型的成员剔掉。
2. Extract 是把满足条件的成员提取出来。
3. NonNullable 本质上就是过滤掉 `null | undefined`。
4. 它们能成立的底层前提是分布式条件类型。

### 代码抓手

```ts
type MyExclude<T, U> = T extends U ? never : T
type MyExtract<T, U> = T extends U ? T : never
type MyNonNullable<T> = T extends null | undefined ? never : T
```

### 常见坑

1. 只记结果，不知道为什么联合类型会逐项过滤。
2. 把 extends 理解成运行时继承关系。
3. 不知道 never 在联合类型里会被消掉。

### 面试展开

我会说：这类题的关键不是过滤逻辑本身，而是你是否理解分布式条件类型。联合类型之所以能被逐项筛选，就是因为裸类型参数触发了分发。

## 9.5 ReturnType、Parameters、InstanceType

### 定位

这一节处理 infer 最常见的落地题。

### 必会结论

1. 这组题的核心是条件类型配合 infer 做模式匹配。
2. ReturnType 提函数返回值，Parameters 提参数元组，InstanceType 提构造函数实例类型。
3. 它们都不是“神奇内置能力”，本质上是可手写的模式提取。

### 代码抓手

```ts
type MyReturnType<T> = T extends (...args: any[]) => infer R ? R : never
type MyParameters<T> = T extends (...args: infer P) => any ? P : never
type MyInstanceType<T> = T extends new (...args: any[]) => infer R ? R : never
```

### 核心理解

看到这类题，脑子里应该立刻想到“我要匹配的是函数结构还是构造函数结构，然后把其中一段类型抓出来”。这就是 infer 的典型用法。资深面试里，如果你能顺手讲出它是在做模式匹配，而不是单纯背模板，层次会高很多。

### 常见坑

1. 把普通函数类型和构造函数类型的匹配模式写混。
2. 不加边界约束，让非函数类型也能传进来。
3. 只会抄模板，不理解 infer 在提取哪一段。

### 面试展开

我会说：这组题都是 infer 的模式提取题。真正关键的是先看目标结构是什么，再决定把哪段类型信息提出来。

## 9.6 第九章速记

### 定位

这一节收束高频类型手写题。

### 必会结论

1. 映射类型类题常见有 Partial、Pick、Readonly、Record。
2. 条件类型过滤类题常见有 Exclude、Extract、NonNullable。
3. infer 提取类题常见有 ReturnType、Parameters、InstanceType。
4. 手写题真正想考的是底层机制，不是死记代码。

### 面试展开

如果让我 30 秒收口这一章，我会说：TS 高频手写题几乎都能归到三类机制上，映射类型、条件类型和 infer。只要把这三类机制理解透，大多数题都能自己推出来。

# 10 高频面试题与分层展开

## 10.1 any 和 unknown 的核心区别是什么，项目里怎么选

### 题目

any 和 unknown 的区别是什么，项目里应该怎么选？

### 考点

1. 是否理解“关闭检查”和“延迟收窄”是两种完全不同的边界语义。
2. 是否知道未知输入应该优先用 unknown。

### 3-5 年回答

any 会关闭类型检查，基本什么都能做；unknown 也能接收任意值，但必须先做类型收窄后才能使用，所以更安全。项目里接第三方输入、接口返回、异常对象时，应该优先用 unknown，而不是直接上 any。

### 5-7 年展开

更资深的说法是：any 是类型系统的逃逸口，它会把很多潜在问题直接吞掉；unknown 则保留了“我现在还不知道它是什么”的边界语义，逼着你在真正使用之前做判定。所以 unknown 更适合边界输入，any 只适合非常短期的迁移兜底。一个项目里如果 any 大量蔓延，说明它没有真正把 TS 当成边界系统使用。

### 高频追问与回答

1. 为什么 `catch (e)` 这类场景更适合 unknown？
   因为异常对象来源不可控，不能假设它一定有某些属性，先用 unknown 再收窄更稳。
2. unknown 会不会让代码变得更麻烦？
   会增加一点显式判断，但这是在把风险暴露出来，而不是把风险藏起来。

### 易错点

1. 把 unknown 理解成“更难用的 any”。
2. 为了图省事直接把所有外部输入都断言成目标类型。

## 10.2 TypeScript 为什么采用结构类型系统

### 题目

TS 为什么是结构类型系统，而不是名义类型系统？

### 考点

1. 是否理解 TS 要贴近 JavaScript 的对象模型。
2. 是否能说出结构类型系统的收益和代价。

### 3-5 年回答

因为 JavaScript 更关注对象有没有这些属性和能力，而不是类型名是不是同一个，所以 TS 采用结构类型系统会更贴近 JS，也更方便渐进接入。

### 5-7 年展开

更完整的回答是：TS 选择结构类型系统，是为了兼容 JavaScript 天然的鸭子类型世界。这样两个结构一致的对象可以自然兼容，类型复用和老代码接入都更顺滑。但代价是它可能显得过于宽松，所以 TS 又补了额外属性检查、只读约束、品牌类型这些能力来平衡边界。这也是为什么资深工程里既要理解结构兼容，也要知道什么时候要人为收紧。

### 高频追问与回答

1. 结构类型系统最大的问题是什么？
   容易过宽松，尤其是不同领域值结构相同但语义不同时。
2. 怎么弥补这个问题？
   可以用品牌类型、只读约束、判别联合和更明确的边界建模。

### 易错点

1. 只说“因为这样更灵活”，没有解释和 JS 的关系。
2. 不知道对象字面量还有额外属性检查这层补偿机制。

## 10.3 泛型约束和分布式条件类型分别解决什么问题

### 题目

泛型约束和分布式条件类型分别解决什么问题？

### 考点

1. 是否理解“抽象但不失控”和“联合逐项过滤”是两类不同问题。
2. 是否能把 keyof 约束、Exclude 过滤串起来讲。

### 3-5 年回答

泛型约束解决的是泛型过宽导致不安全的问题，比如约束 key 必须来自对象自身属性。分布式条件类型解决的是联合类型逐项过滤和提取的问题，比如 Exclude、Extract。

### 5-7 年展开

更资深的说法是：泛型约束是在保持抽象能力的同时，加上一层最小必要边界，避免泛型变成“什么都能传”的空壳；分布式条件类型则让类型系统能像过滤器一样，对联合类型成员逐项求值。前者偏“约束输入边界”，后者偏“计算输出结果”，两者经常组合使用。

### 高频追问与回答

1. 为什么 Exclude 能逐项过滤联合类型？
   因为条件类型左侧是裸类型参数时，会触发分布式求值。
2. 泛型约束是不是越多越好？
   不是，约束的目标是最小但必要，过多会让抽象能力反而变差。

### 易错点

1. 把泛型约束和条件类型混成一种机制。
2. 只会背 Exclude 模板，不知道为什么会分发。

## 10.4 strict 为什么必须开

### 题目

为什么说中大型 TS 项目最好开 strict？

### 考点

1. 是否理解严格模式暴露的是高价值问题。
2. 是否能从长期维护角度回答，而不是只从“报错更多”出发。

### 3-5 年回答

strict 会把很多问题提前暴露出来，比如空值、隐式 any、函数兼容和 this 上下文问题。项目越大、协作越多，越应该开。

### 5-7 年展开

更完整的回答是：strict 的价值不在于“让编译更严格”，而在于把很多长期维护成本很高的问题前移到编译期。大型项目里，null/undefined、隐式 any、函数参数不安全、类属性未初始化这类问题，都会在重构和协作中放大。关闭 strict 也许能短期提速，但长期会让类型系统逐渐失去约束力，最后 TS 只剩提示作用。

### 高频追问与回答

1. 老项目开不了 strict 怎么办？
   可以分阶段治理，优先收紧高风险模块，而不是整体关闭。
2. 开了 strict 但到处用 `!` 和 as 算不算真严格？
   不算，这只是把问题从显性改成了隐性。

### 易错点

1. 只说“能减少 bug”，没有解释具体是哪类 bug。
2. 把严格模式理解成单个开关，而不知道里面有多项关键子规则。

## 10.5 TS 和运行时校验是什么关系

### 题目

用了 TypeScript 以后，还需不需要运行时校验？

### 考点

1. 是否清楚 TS 只存在于编译期。
2. 是否能说出哪些输入仍然需要运行时验证。

### 3-5 年回答

需要。因为 TS 只保证编译期类型一致性，不保证接口返回、用户输入、URL 参数、本地存储等外部数据在运行时一定正确。

### 5-7 年展开

更资深的说法是：TS 和运行时校验解决的是两个不同层面的问题。TS 约束的是“我们内部代码是否按声明协作”，运行时校验约束的是“外部世界给我们的数据是否真实可信”。只要数据来自网络、用户、存储、SDK 或跨边界系统，就应该考虑运行时校验。真正成熟的做法，是让静态类型和运行时 schema 尽量形成联动，而不是写成两套互相脱节的系统。

### 高频追问与回答

1. 哪些场景最该做运行时校验？
   接口返回、表单输入、URL 查询参数、本地缓存反序列化、第三方 SDK 返回。
2. 常见方案有哪些？
   zod、valibot，或者团队自定义 schema validator。

### 易错点

1. 以为后端有文档就等于运行时一定可靠。
2. 用 as 直接把未知输入断成目标类型。

## 10.6 satisfies 和 as 有什么本质区别

### 题目

satisfies 和 as 有什么区别，分别适合什么场景？

### 考点

1. 是否理解“结构校验”和“强制断言”语义不同。
2. 是否知道 satisfies 的价值是保留原始精确信息。

### 3-5 年回答

as 更像强制类型断言，是在告诉编译器“相信我”；satisfies 是校验某个值满足某个类型约束，但尽量保留原值的精确推断结果。

### 5-7 年展开

更完整的回答是：as 本质上带有逃逸意味，它常用于你比编译器更清楚某个值的真实类型，但也容易被滥用。satisfies 的价值则是“在不丢精确字面量信息的前提下做结构校验”，它特别适合路由表、配置表、映射表、常量对象这类场景。也就是说，一个偏“断言”，一个偏“验证”。

### 高频追问与回答

1. satisfies 会不会把最终类型直接变成右侧类型？
   不会，它主要做约束校验，原值往往还保留更精确的推断信息。
2. 能不能完全不用 as？
   不能，某些边界场景仍然需要，但应克制使用。

### 易错点

1. 把两者说成只是写法不同。
2. 不知道 satisfies 最大的价值是“校验但不粗暴变宽”。

## 10.7 判别联合为什么比堆可选字段更稳

### 题目

为什么说判别联合比“一个接口里堆很多可选字段”更稳？

### 考点

1. 是否理解非法状态组合问题。
2. 是否能把状态建模和控制流收窄联系起来。

### 3-5 年回答

因为判别联合可以明确不同状态对应不同结构，能让非法状态组合在类型层面消失，也更方便 switch 做收窄和穷尽检查。

### 5-7 年展开

更资深的说法是：可选字段堆叠看起来省事，但它其实默认允许很多不该出现的结构，比如成功状态没有数据、失败状态却同时有数据和错误信息。判别联合则把每种状态的字段边界写死，再配合统一的 status 或 type 字段做控制流收窄，这样不但消费端代码更自然，后续扩展新状态时也更安全。

### 高频追问与回答

1. 判别联合适合哪些场景？
   请求状态、组件渲染状态、节点类型、命令类型、多分支业务结果。
2. 判别联合一定要用 status 字段吗？
   不一定，也可以用 type、kind 等稳定判别键，关键是统一且可区分。

### 易错点

1. 只说“更好维护”，没有说清非法状态组合为什么会消失。
2. 判别字段被拓宽成 string，导致收窄能力丢失。

## 10.8 第十章收口

### 题目

如果让你用一句话收口 TypeScript 的资深主线，你会怎么说？

### 3-5 年回答

TypeScript 最重要的是把复杂系统里的边界提前在编译期暴露出来。

### 5-7 年展开

更完整的收口是：资深 TS 能力不在于会背多少语法，而在于能否把类型设计、工程配置和运行时边界一起讲清楚。真正拉开差距的，不是写得多复杂，而是边界建得稳、团队能维护、系统能长期演进。

### 易错点

1. 把 TS 理解成“高级注释系统”。
2. 只讲语法，不讲工程和运行时边界。
